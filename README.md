# assistant-low-vision-platform

Шлюз системы голосового описания сцены для людей с нарушениями зрения: принимает снимки и речь от мобильного приложения, вызывает сервисы ИИ-моделей и языковую модель и возвращает ответ речью.

## Назначение

Шлюз - единственная точка входа мобильного приложения (шаблон API Gateway):
- держит с приложением WebSocket-сессию по протоколу `alv.v1`: снимки и аудио идут бинарными кадрами, команды и ответы - JSON-сообщениями;
- вызывает сервисы [objects-detector](https://github.com/nikarpoff/objects-detector) (обнаружение объектов), [asr-service](https://github.com/nikarpoff/asr-service) (распознавание речи) и [tts-service](https://github.com/nikarpoff/tts-service) (синтез речи);
- строит описание сцены по шаблону (`template`), языковой моделью по тексту (`llm`) или мультимодальной моделью по снимку (`vlm`). Языковая модель - облачный поставщик по OpenAI-совместимому API: Polza.ai напрямую или GigaChat через прокси gpt2giga;
- в пассивном режиме предупреждает об опасностях по правилам, без языковой модели;
- пишет журнал запросов и замеры этапов в PostgreSQL. Снимки и аудио не сохраняются никогда;
- отдаёт метрики Prometheus, статистику по журналу и снимок конфигурации стенда.

В репозитории также лежат развёртывание всей системы (`deployments/`), эталонные контракты сервисов (`testdata/contracts/`) и инструменты эксперимента. Требования - в [docs/spec.md](docs/spec.md).

Состояние: версия 0.1.0 в разработке. Шлюз собран целиком: WebSocket-сессия `/v1/session`, конвейеры описания по касанию, вопроса и пассивного режима с цепочкой деградации PLT-9, журнал в PostgreSQL (запросы, сессии, `client.metrics`, снимки конфигурации), `/health`, `/ready`, `/metrics`, `/v1/stats` и `/v1/config`.

## Стек технологий

- **Язык**: Go 1.24
- **HTTP и WebSocket**: gorilla/mux, gorilla/websocket
- **Конфигурация**: переменные окружения (caarlos0/env)
- **Логирование**: собственный printf-логгер `internal/logger`
- **Метрики**: prometheus/client_golang
- **Журнал**: PostgreSQL, драйвер jackc/pgx v5 (`pgxpool`)
- **Валидация**: go-playground/validator
- **Тесты**: testify (require), moq
- **Образ**: distroless (`gcr.io/distroless/static-debian12:nonroot`), публикуется в `ghcr.io/nikarpoff/assistant-low-vision-platform`

## Быстрый старт

Без токенов и без языковой модели (режим `template`):

```bash
docker build -f build/Dockerfile -t alv-platform:dev .
docker run --rm -p 127.0.0.1:8080:80 \
  -e APP_AUTH_DISABLED=true -e APP_DESCRIBER_MODE=template \
  alv-platform:dev
curl http://127.0.0.1:8080/health
```

Без Docker:

```bash
APP_SERVER_PORT=8080 APP_AUTH_DISABLED=true APP_DESCRIBER_MODE=template go run ./cmd/gateway
```

## <a id="env"></a> Переменные окружения

Все настройки - переменные окружения с рабочими значениями по умолчанию. Длительности с суффиксом `_MS` - в миллисекундах, с `_S` и `_TIMEOUT` - в секундах.

Шлюз не стартует и пишет понятную ошибку, если:
- `APP_DESCRIBER_MODE` не `template`, `llm` или `vlm`;
- в режиме `llm` пуст `APP_LLM_MODEL`, в режиме `vlm` пусты и `APP_VLM_MODEL`, и `APP_LLM_MODEL`: идентификатор модели входит в `config_id`, поэтому значения по умолчанию у него нет;
- в режимах `llm` и `vlm` `APP_LLM_URL` - не абсолютный адрес со схемой `http` или `https`;
- `APP_AUTH_DISABLED` не `true`, а `APP_DEVICE_TOKENS` или `APP_ADMIN_TOKEN` пусты;
- `APP_LOG_LEVEL` - не уровень логирования;
- значение числовой или логической переменной не разбирается.

Пустой `APP_LLM_API_KEY` допустим (заглушка поставщика), но в режимах `llm` и `vlm` при старте в лог пишется предупреждение. В режиме `template` настройки языковой модели не проверяются и не используются.

### Языковая модель

| Переменная | Описание | По умолчанию | Обязательная |
|---|---|---|---|
| `APP_LLM_URL` | Базовый адрес OpenAI-совместимого API поставщика; к нему добавляются `/chat/completions` и `/models` | `https://polza.ai/api/v1` | Нет |
| `APP_LLM_API_KEY` | Ключ поставщика (секрет): ключ Polza.ai или ключ доступа к gpt2giga | пусто | Нет |
| `APP_LLM_MODEL` | Идентификатор модели для режима `llm` | пусто | Да, в режимах `llm` и `vlm` (если пуст `APP_VLM_MODEL`) |
| `APP_VLM_MODEL` | Идентификатор мультимодальной модели для режима `vlm`; пусто - `APP_LLM_MODEL` | пусто | Нет |
| `APP_LLM_TEMPERATURE` | Температура генерации | `0` | Нет |
| `APP_LLM_SEED` | Seed генерации | `42` | Нет |
| `APP_LLM_MAX_TOKENS` | Предел токенов ответа | `96` | Нет |
| `APP_LLM_EXTRA_BODY` | JSON-объект, добавляемый в тело запроса (например, выключение рассуждений). Поля `model`, `messages`, `stream`, `temperature`, `top_p`, `seed`, `max_tokens` и `user` в нём запрещены: их задаёт клиент или они не передаются поставщику | `{}` | Нет |

Клиент языковой модели (`internal/llm`) один для любого поставщика:
- шлёт `POST <APP_LLM_URL>/chat/completions` с `stream: true`, моделью, сообщениями промпта, `temperature`, `top_p` (всегда 1, DSC-5), `seed`, `max_tokens` и полями `APP_LLM_EXTRA_BODY`;
- из своих заголовков ставит только `Authorization: Bearer <APP_LLM_API_KEY>` (при пустом ключе не ставит), `Content-Type: application/json` и `Accept: text/event-stream`. `X-Request-ID`, `device_id`, `label` и поле `user` поставщику не передаются;
- читает SSE построчно: комментарии и пустые строки пропускает, поле `error` проверяет в каждом фрагменте, `model` и `system_fingerprint` берёт из первого фрагмента, где они есть;
- держит пул keep-alive соединений, проверяет TLS-сертификат по системным корневым сертификатам, не сжимает ответ, не следует перенаправлениям и не повторяет запрос;
- первый токен ждёт не дольше `APP_LLM_TTFT_TIMEOUT_MS`, всю генерацию - не дольше `APP_LLM_TOTAL_TIMEOUT_MS`.

Вид отказа (`reason`) пишется в журнал (`llm_error`) и в метрику `alv_upstream_errors_total{upstream="llm", reason}`:

| `reason` | Что случилось |
|---|---|
| `insufficient_balance` | HTTP 402 до потока или событие ошибки в потоке с `code` `INSUFFICIENT_BALANCE`, `402` (число или строка) или `PAYMENT_REQUIRED` |
| `http_429` | HTTP 429 до потока |
| `http_5xx` | HTTP 500-599 до потока |
| `http_4xx` | другой не-2xx статус до потока (400, 401, 403, 404, 408, 413, перенаправление) |
| `stream_error` | HTTP 200 и фрагмент с полем `error` или `finish_reason: "error"`, даже если за ним пришёл `data: [DONE]` |
| `disconnect` | соединение не установлено, закрылось или поток не прочитался до `[DONE]` и до фрагмента с `finish_reason` |
| `empty` | нормальный конец без текста (или только с пробелами) |
| `timeout_ttft` / `timeout_total` | нет первого токена за `APP_LLM_TTFT_TIMEOUT_MS` / генерация дольше `APP_LLM_TOTAL_TIMEOUT_MS` |

В лог при отказе пишутся `request_id`, `reason`, HTTP-статус, `code` и `trace_id` поставщика, а при сетевом сбое - ошибка соединения. Текст ошибки поставщика не пишется никогда.

## Протокол `alv.v1`

Приложение держит одно WebSocket-соединение `wss://<хост>/v1/session` с подпротоколом `alv.v1` и токеном устройства в `Authorization: Bearer <токен>`. Текстовые кадры - JSON-сообщения с полем `type` (от приложения - `hello`, `describe`, `ask.start`, `ask.end`, `cancel`, `client.metrics`; от Шлюза - `welcome`, `accepted`, `transcript`, `answer.start`, `answer.text`, `answer.end`, `error` и другие). Бинарные кадры - заголовок 22 байта (версия, вид, `request_id`, `seq`) и полезная нагрузка: JPEG снимка, PCM вопроса или PCM ответа.

Полное описание - раздел PROTO в [docs/spec.md](docs/spec.md). Эталонные вектора кадров и сообщений, общие с приложением, - `testdata/protocol/vectors.json`.

### Сессия

`internal/session` (PLT-1) обслуживает `GET /v1/session`:
- до upgrade проверяются токен устройства (`401 {"error": "unauthorized"}`, сравнение в постоянное время; при `APP_AUTH_DISABLED=true` токен не нужен) и подпротокол: клиент обязан предложить `alv.v1`, иначе `400`. Сжатие `permessage-deflate` выключено;
- первое сообщение - `hello`. Ответ - `welcome` с `session_id`, `server_version`, `config_id` текущего снимка конфигурации и `config` для приложения (размер и качество снимка, интервал пассивного режима, окно и предел вопроса, форматы аудио). `hello` с другой версией `protocol` - `error` с кодом `unsupported_protocol` и закрытие с кодом 4001;
- сообщение или кадр до `hello`, неизвестный `type`, кадр короче 22 байт, неизвестные версия или вид кадра, AUDIO_OUT от приложения, кадр без ожидающего его запроса - `error` с кодом `bad_request`, соединение не закрывается. Снимок больше `APP_MAX_IMAGE_BYTES`, фрагмент аудио больше 64 КиБ, вопрос длиннее `APP_MAX_QUESTION_MS` - `payload_too_large`, запрос завершается;
- в сессии одна горутина чтения и одна записи. Новый пользовательский запрос (`describe` с `mode=on_demand` или `ask.start`) и `cancel` отменяют текущий: его вызовы сервисов прерываются, писатель отбрасывает все его сообщения и кадры, запрос считается со статусом `cancelled`. Пассивный запрос во время пользовательского или другого пассивного получает `passive.clear` с `reason=skipped` и попадает в журнал со статусом `skipped`. В журнал попадает каждый запрос: отклонённый до запуска конвейера (снимок больше лимита, слишком длинный вопрос, `busy` при остановке) - со статусом `error` и кодом ошибки, отменённый до снимка или до `ask.end` (`cancel`, новый запрос, закрытие сессии) - со статусом `cancelled`. Закрытая сессия ждёт свои отменённые конвейеры до 2 с и только потом пишет конец сессии, а остановка Шлюза ждёт закрытые сессии, поэтому записи не теряются при остановке журнала. Запрос считается завершённым до отправки своего последнего сообщения (`answer.end`, `passive.clear` или `error`), поэтому следующий запрос, отправленный сразу после него, не получает ложный `skipped` и не отменяет уже ответивший;
- Шлюз шлёт ping каждые 15 с и закрывает соединение, если pong не пришёл за 30 с;
- реестр сессий ведёт `alv_sessions_active`. По SIGTERM Шлюз перестаёт принимать сессии (`503`) и новые запросы (`busy`), даёт активным запросам до 5 с и закрывает сессии с кодом 1001 после уже поставленных в очередь сообщений.

### Конвейер описания по касанию

`internal/pipeline` (PLT-2, PLT-7, PLT-14): `describe` → снимок → `accepted` → детектор → описание сцены → поток предложений → TTS → AUDIO_OUT → `answer.end`.
- Текст описания очищается (DSC-7): блоки `<think>...</think>`, символы `*`, `_`, `#`, `` ` ``, маркеры списков и эмодзи удаляются, пробелы схлопываются.
- Поток режется на предложения после `.`, `!`, `?`, `…`, за которыми идёт пробел или конец потока. Предложение короче 12 символов склеивается со следующим, кроме последнего. В ответе не больше 3 предложений и `APP_MAX_ANSWER_CHARS` символов; при достижении предела поток языковой модели закрывается.
- Каждое готовое предложение сразу уходит в TTS, одновременно не больше 2 синтезов на запрос. В приложение идут `answer.start`, затем для каждого предложения по порядку `answer.text` и его кадры AUDIO_OUT; номера кадров идут подряд через весь ответ.
- `answer.end` содержит полный текст, объекты в фокусе (опасности первыми, `hazard=true` только для уровня `danger`), `hazard` и `timings`: `receive_ms`, `queue_ms`, `detect_ms`, `llm_ttft_ms`, `llm_first_sentence_ms`, `llm_total_ms` (режимы `llm` и `vlm`), `tts_first_chunk_ms`, `tts_total_ms`, `server_ttfa_ms`, `server_total_ms`. Те же этапы идут в `alv_stage_duration_seconds{stage, kind}`, итог запроса - в `alv_requests_total{kind, status}`.
- Весь запрос ограничен `APP_REQUEST_DEADLINE_MS` от получения полного входа: превышение до начала ответа - `error` с кодом `upstream_timeout`. Отказы сервисов и поставщика - по разделу «Деградация».
- Описанная сцена (объекты, текст, время снимка) записывается в историю устройства.
- Собственная обработка Шлюза с заглушками сервисов без задержки укладывается в 15 мс p95 (PLT-18, тест `TestOverheadBudget`).

### Конвейер вопроса

PLT-3, PROTO-7: `ask.start` → снимок (если `with_image`) → AUDIO_IN → `ask.end` → `accepted` → `transcript` → ответ.
- Детектор вызывается сразу по получении снимка, пока пользователь ещё говорит. Кадры AUDIO_IN копятся в памяти и по `ask.end` уходят в ASR одним телом.
- Расшифровка даёт намерение (PLT-4). Для команд приложения (`repeat`, `stop`, `passive_on`, `passive_off`) после `transcript` сразу идёт `answer.end` с пустым `text`, без `answer.start` и аудио.
- `describe` - описание сцены, `describe_ahead` - описание с `focus=ahead`, `question` - ответ на вопрос (`answer.start` с `kind=answer`) с текущей сценой и историей устройства. Если детектор ещё работает, Шлюз ждёт его результат.
- Без снимка берётся последняя сцена устройства не старше `APP_SCENE_FRESHNESS_MS`, иначе ответ строится по истории без текущей сцены.
- Пустая расшифровка - `error` с кодом `asr_empty`, недоступный ASR - `asr_unavailable`.
- В историю записываются вопрос и ответ, а при снимке - и новая сцена.

### Пассивный режим

PLT-5, PLT-6, PROTO-8: `describe` с `mode=passive` → снимок → `accepted` → детектор → правила опасности → предупреждение или `passive.clear`. Языковая модель не вызывается.
- Озвучиваются правила уровня `danger`, а уровня `notice` - только при `APP_PASSIVE_NOTICES=true`. Предупреждение - `answer.start` с `kind=warning` и `priority=high` (только `notice` - `priority=normal`), затем `answer.text` и аудио каждой фразы, затем `answer.end`. Фраза правила уходит в TTS без точки, как в кэше прогрева; в `answer.text` - с точкой.
- Повтор по паре «класс, направление» подавляется на `APP_HAZARD_COOLDOWN_MS`, кроме приближения `far` → `near`. Cooldown ведётся по `device_id`, как история, и переживает переподключение.
- `passive.clear` с причиной: `no_hazard` - нечего озвучивать, `cooldown` - всё подавлено, `skipped` - в сессии идёт пользовательский или другой пассивный запрос, `stale` - с получения снимка по часам Шлюза прошло больше `APP_PASSIVE_DEADLINE_MS`. Устаревший результат не отправляется, даже если синтез уже начался.

### Деградация

PLT-9:

| Что случилось | Ответ |
|---|---|
| поставщик не дал первый токен за `APP_LLM_TTFT_TIMEOUT_MS` или первое предложение за `APP_LLM_TOTAL_TIMEOUT_MS` | описание по шаблону, `degraded_reason=llm_timeout` |
| отказ поставщика до первого готового предложения (402, 429, 5xx, другой не-2xx, событие ошибки, обрыв, пустой ответ) | описание по шаблону, `degraded_reason=llm_unavailable` |
| отказ поставщика после первого готового предложения | ответ закрывается готовыми предложениями, хвост отбрасывается, `llm_unavailable` |
| `APP_LLM_TOTAL_TIMEOUT_MS` истёк после первого готового предложения | так же, `llm_timeout` |
| TTS недоступен или не дал первый фрагмент вовремя | `answer.start` с `audio: null`, только `answer.text`, `tts_unavailable` |
| детектор недоступен, режим `template` или `llm`; пассивный режим | `error` с кодом `detector_unavailable` |
| детектор недоступен, режим `vlm` | описание по снимку без подсказок детектора |
| ASR недоступен / пустая расшифровка | `error` с кодом `asr_unavailable` / `asr_empty` |
| превышен `APP_REQUEST_DEADLINE_MS` до начала ответа | `error` с кодом `upstream_timeout` |

- Готовое предложение - выделенное из потока по PLT-7 и переданное в TTS. Предложение, которое закончилось знаком конца прямо перед отказом, тоже готово: поток кончился после него.
- Повторных запросов к поставщику нет. Вид отказа PLT-15 пишется в запись журнала (`llm_error`).
- Ответ несёт одну причину: отказ языковой модели важнее отказа TTS. Отсутствие звука и так видно по `audio: null` в `answer.start`.

| GET | `/metrics` | Метрики Prometheus | да |

Подробности - PLT-13 в [docs/spec.md](docs/spec.md). Ошибка `500` всегда обезличена: `{"error": "internal server error"}`, подробности только в логе; паника обработчика тоже даёт такой ответ. `/health`, `/ready` и `/metrics` работают без токена.

### GET /ready

Детектор, ASR и TTS опрашиваются при каждом запросе одновременно (`GET /v1/info` с токеном сервиса, не дольше 2 с). `llm` - результат последнего `GET <APP_LLM_URL>/models` с ключом поставщика: проверка идёт при старте и раз в `APP_CONFIG_REFRESH_S` по тому же пулу keep-alive соединений, что и запросы к модели, и не даёт соединению закрыться по простою (PLT-15). До первой проверки `llm` - `down`, в режиме `template` - `disabled`. `journal` - состояние писателя журнала: `ok` после успешной записи или миграции, `down` при недоступной базе, `disabled` при пустом `APP_POSTGRES_DSN`.

```json
{"status":"ready","detector":"ok","asr":"ok","tts":"ok","llm":"ok","journal":"ok","vocabulary":"loaded"}
```

- `detector`, `asr`, `tts`, `llm`, `journal` - `ok`, `down` или `disabled`; `vocabulary` - `loaded` или `not_loaded`; `status` - `ready` или `not_ready`.
- `200`, если словарь загружен и отвечают ASR, TTS и детектор (в режиме `vlm` детектор не обязателен); иначе `503`. `llm` и `journal` на код не влияют: без них Шлюз деградирует (PLT-9).

### GET /v1/config

Текущий снимок конфигурации стенда (PLT-12), заголовок `Authorization: Bearer <APP_ADMIN_TOKEN>`; без него - `401`. Метка варианта размещения - поле `placement` верхнего уровня `config`. Ключей, токенов и пароля базы в снимке нет.

```bash
curl -H "Authorization: Bearer $APP_ADMIN_TOKEN" http://127.0.0.1:8080/v1/config
```

```json
{"config_id":"c9f2a1d0e3b4","collected_at":"2026-11-01T10:00:00Z","config":{"placement":"B","describer_mode":"llm","llm":{"url":"https://polza.ai/api/v1","model":"qwen/qwen3-8b"},"...":"..."}}
```

Коды: `200`; `401` - нет админ-токена; `503` - снимок ещё не собран; `500` - обезличенная ошибка.

### GET /v1/stats

Статистика по журналу для отчёта по конфигурации (PLT-13, EXP-5, EXP-8). Нужен заголовок `Authorization: Bearer <APP_ADMIN_TOKEN>`; без него или с другим токеном - `401` и `{"error": "unauthorized"}`. При `APP_AUTH_DISABLED=true` токен не проверяется.

Параметры запроса, все необязательные; пустой параметр не фильтрует:

| Параметр | Описание |
|---|---|
| `since` | Начало интервала по времени создания запроса, RFC 3339 (`2026-11-01T10:00:00Z`), включительно |
| `until` | Конец интервала, RFC 3339, не включительно; должен быть позже `since` |
| `kind` | Вид запроса: `describe` (по касанию), `ask`, `passive` |
| `config_id` | Конфигурация стенда |

```bash
curl -H "Authorization: Bearer $APP_ADMIN_TOKEN" \
  "http://127.0.0.1:8080/v1/stats?config_id=c9f2a1d0e3b4&since=2026-11-01T10:00:00Z&until=2026-11-01T12:00:00Z"
```

```json
{"config_id":"c9f2a1d0e3b4","since":"2026-11-01T10:00:00Z","until":"2026-11-01T12:00:00Z","kind":null,"stages":{"detect_ms":{"n":300,"p50":38.1,"p95":61.0,"mean":40.2}},"e2e":{"describe":{"n":300,"p50":1310.0,"p95":1820.0,"mean":1350.4}},"degraded":{"llm_timeout":{"n":9,"share":0.03},"llm_unavailable":{"n":3,"share":0.01},"tts_unavailable":{"n":0,"share":0.0}},"llm_errors":{"timeout_ttft":9,"http_429":2,"insufficient_balance":1},"llm_fallback_share":0.04,"llm_models":{"fake/fake-llm":312}}
```

Форма ответа - контракт для инструментов эксперимента, её закрепляет копия примера `testdata/stats/stats.response.json`:
- `config_id`, `since`, `until`, `kind` - применённые фильтры, `null` - фильтра нет; время - в UTC;
- `stages` - для каждого этапа PLT-14 из журнала: число замеров `n`, `p50`, `p95` и среднее `mean` в мс;
- `e2e` - то же по `trigger_to_first_audio_ms` из `client.metrics`, по видам запроса;
- `degraded` - для каждого `degraded_reason` (`llm_timeout`, `llm_unavailable`, `tts_unavailable`, ключи есть всегда) число ответов и их доля от всех ответов выборки. Ответ - запрос, закончившийся `answer.end`, то есть со статусом `ok` или `degraded`;
- `llm_errors` - число ответов по каждому виду отказа поставщика `llm_error` (PLT-15);
- `llm_fallback_share` - доля откатов: ответы с `degraded_reason` `llm_timeout` или `llm_unavailable`, делённые на все ответы описания сцены в режимах `llm` и `vlm` (`describe` по касанию и `ask` с намерением `describe`, `describe_ahead` или `question`); `null`, если таких ответов нет;
- `llm_models` - число запросов по каждому значению `model` из ответов поставщика.

Перцентили считаются методом nearest-rank: `x[ceil(q·n)-1]` по отсортированной выборке; `p50`, `p95` и `mean` округлены до 0,1 мс. Долю откатов считает функция `stats.FallbackShare` - та же, что у `loadgen` и `score`.

Коды ответа: `200`; `401` - нет админ-токена; `422` - неверный параметр (`{"error": "validation failed for fields: since"}`) или `until` не позже `since`; `503` - журнал выключен (`APP_POSTGRES_DSN` пуст); `500` - обезличенная внутренняя ошибка.

### Метрики

Все метрики объявлены в `internal/metrics` в собственном реестре и отдаются `GET /metrics`:

| Метрика | Тип | Метки |
|---|---|---|
| `alv_stage_duration_seconds` | гистограмма | `stage`, `kind` |
| `alv_e2e_duration_seconds` | гистограмма | `kind`, `network` |
| `alv_requests_total` | счётчик | `kind`, `status` |
| `alv_upstream_errors_total` | счётчик | `upstream`, `reason` |
| `alv_sessions_active` | показатель | - |
| `alv_journal_dropped_total` | счётчик | - |

`alv_e2e_duration_seconds` наполняет `client.metrics` приложения: `trigger_to_first_audio_ms` в секундах, `kind` - вид запроса с этим `request_id` в той же сессии (сессия помнит виды последних 64 запросов), `network` - из сообщения. Для `upstream="llm"` значения `reason` - виды отказа PLT-15; проверки `/models` в этот счётчик не входят.

### Журнал

Журнал (PLT-11) пишется асинхронно, запрос не ждёт базу:
- сессия - при `hello` (устройство, версия приложения, сеть, `label`) и её конец при закрытии соединения;
- запрос - когда конвейер закончил: статус, этапы, `image_bytes` (только размер снимка), расшифровка, ответ, объекты, `config_id`, `llm_model`, `llm_system_fingerprint`, `llm_error`;
- `client.metrics` - в `client_metric` по имени метрики;
- снимок конфигурации - при старте и при каждом обновлении (`ON CONFLICT DO NOTHING` по `config_id`).

Снимки и аудио не сохраняются никогда: ни в базе, ни файлами, ни в логе; настройки, которая бы это включала, нет (NFR-8).
## Сервисы ИИ-моделей

Клиенты детектора, ASR и TTS лежат в `internal/upstream/{detector,asr,tts}` (PLT-15 в [docs/spec.md](docs/spec.md)):
- у каждого сервиса свой пул keep-alive соединений, без прокси и без сжатия;
- тела бинарные, без base64:
  - снимок детектору - `image/jpeg` как есть;
  - вопрос в ASR - `audio/L16; rate=16000; channels=1`;
  - в TTS - JSON TTS-1 (`text`, `voice`, если задан `APP_TTS_VOICE`, `sample_rate` из `APP_AUDIO_OUT_SAMPLE_RATE`, `format: pcm_s16le`, `speed: 1.0`), ответ - поток `audio/L16`;
- заголовки: `Authorization: Bearer <APP_*_TOKEN>` (при пустом токене не ставится) и `X-Request-ID` - UUID запроса приложения;
- таймауты PLT-8:
  - детектор - `APP_DETECT_TIMEOUT_MS`, ASR - `APP_ASR_TIMEOUT_MS` на весь вызов;
  - TTS - `APP_TTS_FIRST_CHUNK_TIMEOUT_MS` до первого аудиофрагмента. Клиент возвращает поток, как только пришёл первый фрагмент, остальное ограничено только дедлайном запроса. Фрагменты содержат целые отсчёты (чётное число байт);
  - `GET /v1/info` и `GET /v1/vocabulary` - 2 с;
- повторов нет. Каждый отказ - типизированная ошибка и `+1` к `alv_upstream_errors_total{upstream, reason}`, где `upstream` - `detector`, `asr` или `tts`:

| Что случилось | Ошибка | `reason` |
|---|---|---|
| ответ 503 (очередь сервиса заполнена) | `ErrBusy` | `busy` |
| другой ответ 5xx, нет соединения, поток оборвался | `ErrUnavailable` | `unavailable` |
| вызов или первый фрагмент TTS не уложился в таймаут | `ErrTimeout` | `timeout` |
| ответ 401 (неверный токен сервиса) | `ErrUnauthorized` | `unauthorized` |
| другой не-2xx ответ (400, 413, 415, 422) | `ErrRejected` | `rejected` |
| ответ 2xx с другим `Content-Type`, битым JSON или пустым потоком | `ErrInvalidResponse` | `invalid_response` |

Вызов, прерванный самим Шлюзом (отмена запроса или его дедлайн), отказом сервиса не считается и в счётчик не попадает. Поле `detail` ответа сервиса попадает в текст ошибки.

### Словарь детектора

`internal/vocabulary` (PLT-16, DET-2) загружает словарь при старте запросом `GET /v1/vocabulary`. Пока словарь не загружен, попытки повторяются с паузой, которая удваивается от 0,5 до 10 с; каждая неудача пишется в лог предупреждением. Словарь проверяется: уникальные `id` в snake_case, формы `one`, `few`, `many`, род `m`, `f`, `n` или `pl`, компилируемые шаблоны `mentions`.

Словарь даёт:
- форму названия для количества по правилам русского языка: 1 «стул», 2 «стула», 5 и 11 «стульев», 21 «стул»;
- классы для проверки правил опасности;
- сопоставитель упоминаний. Шаблоны `mentions` применяются к тексту, нормализованному по PLT-4, и оборачиваются в `(?:^| )(?:<шаблон>)(?: |$)`: RE2 не знает `\b` для кириллицы, поэтому границы слов - пробелы и края текста.

## Намерения, опасности, история

### Нормализация текста

`internal/textnorm` (PLT-4, ASR-4): нижний регистр, `ё` → `е`, знаки Unicode-категорий `P*` заменяются пробелом, символы `S*` (`№`, `+`) и цифры остаются, пробелы (включая неразрывный) схлопываются. Правило общее с ASR и закреплено таблицей `testdata/contracts/asr-service/normalize.cases.json`.

### Намерения

`internal/intent` (PLT-4) сравнивает нормализованную расшифровку с фразами команд из `configs/intents.yaml` (встроен в бинарник, путь переопределяет `APP_INTENTS_PATH`). Команда распознаётся и с «пожалуйста» в начале или в конце; любой другой непустой текст - `question`, пустой после нормализации - ошибка `ErrEmptyText` (код `asr_empty`). Фразы в файле нормализуются при загрузке. Ошибки старта: неизвестное намерение (`question` в файле не задаётся), фраза двух намерений, фраза, пустая после нормализации, файл без фраз.

### Правила опасности

`internal/hazard` (PLT-5, PLT-6) читает `configs/hazard_rules.yaml` (путь переопределяет `APP_HAZARD_RULES_PATH`). Правило: `name`, `classes`, `directions` и `distances` (пусто - любое), `min_confidence`, `level` (`danger` или `notice`), `phrase` с подстановками `{direction}` («слева», «впереди», «справа») и `{object}` (форма `ru.one` словаря). Неизвестные поля - ошибка разбора. Классы сверяются со словарём детектора после его загрузки; неизвестный класс - ошибка с именем правила.

- Если объект подпадает под несколько правил, побеждает первое правило `danger`, иначе первое `notice`.
- Совпадения упорядочены как в DSC-2: `danger`, затем `notice`; `near` раньше `far`; по убыванию площади.
- Фразы без точки в конце и совпадают с контрактом прогрева TTS `testdata/contracts/tts-service/prewarm_phrases.txt` (проверяет `TestHazardPolicy/must_pass_prewarm_phrases_contract`). При изменении правил обновите контракт и запустите `scripts/sync-contracts.sh`.
- Cooldown ведётся по паре «класс, направление»: предупреждение звучит не чаще раза в `APP_HAZARD_COOLDOWN_MS`. Исключение - пара была `far` в последнем кадре, где её видели, а теперь `near`. Поэтому в cooldown передаются все объекты кадра, а не только опасности.

### История

`internal/history` (PLT-10) хранит в памяти по `device_id` последние `APP_HISTORY_SCENES` сцен (объекты, описание, время) и `APP_HISTORY_TURNS` реплик (каждый вопрос и каждый ответ - отдельная реплика). Активность устройства - запись сцены или реплики и `Touch` (например, при переподключении); чтение активностью не считается. Через `APP_HISTORY_TTL_S` без активности история устройства удаляется.

### Хеши файлов

Хеш `configs/hazard_rules.yaml` и `configs/intents.yaml` - первые 12 hex-символов SHA-256 от байтов загруженного файла (`Rules.Hash()`, `Matcher.Hash()`); они входят в снимок конфигурации как `hazard_rules_hash` и `intents_hash`.

## Описание сцены

`internal/describer` (DSC) строит описание сцены в режиме `APP_DESCRIBER_MODE` и отдаёт его потоком текста: предложения режет, очищает и ограничивает конвейер (PLT-7, DSC-7). На вход - объекты детектора, `focus`, вопрос, история устройства и снимок (только `vlm`); идентификаторов устройства, участника и запроса во входе нет (NFR-8).

- Объекты упорядочены как в DSC-2: опасности (правила уровня `danger`), затем `near` раньше `far`, затем по убыванию площади. При `focus=ahead` остаются только объекты с `direction=ahead`.
- **`template`** (DSC-4) - без языковой модели:
  - до двух опасностей фразами правил опасности: «Осторожно, впереди ступени.»;
  - до пяти остальных объектов группами «впереди», «слева», «справа» с количеством словами и формами словаря: «Впереди стол и два стула, слева шкаф.»;
  - вопросы со словом «где» или «есть» («где X», «есть ли X», «X есть») про класс словаря: «Дверь справа, далеко.», «Да, дверь справа, далеко.», «Двери не вижу.» (родительный падеж - форма `few`, у `pl` - `many`). Другие вопросы получают описание сцены;
  - без объектов: «Ничего примечательного не вижу. Попробуйте повернуть телефон.»;
  - шаблонное описание - и откат режимов `llm` и `vlm` (PLT-9): `Describer.Template`.
- **`llm`** (DSC-5): системная часть `prompts/<APP_PROMPT>/system.txt` постоянна и идёт первым сообщением, пользовательская собирается из `user.tmpl` (`text/template`): объекты в компактном виде («ступени - впереди, близко, опасность; стул - слева, далеко»), фокус, сводка до двух предыдущих сцен (описание, а без него - объекты), реплики диалога, вопрос или «Опиши обстановку». Модель - `APP_LLM_MODEL`; параметры генерации и `APP_LLM_EXTRA_BODY` добавляет клиент `internal/llm`.
- **`vlm`** (DSC-6): как `llm`, но сообщение пользователя - текст и снимок `image_url` с data URL `data:image/jpeg;base64,...`; объекты детектора идут подсказками при `APP_VLM_WITH_DETECTIONS=true`; без детектора описание строится по снимку. Модель - `APP_VLM_MODEL`, пусто - `APP_LLM_MODEL`.
- Отказ поставщика возвращается ошибкой `internal/llm` (`ErrTimeout`, `ErrUnavailable`) вместе с уже полученным текстом; откат решает конвейер.
- Поля шаблона `user.tmpl`: `.Objects`, `.FocusAhead`, `.Scenes`, `.Turns`, `.Question`, `.Image`. Неизвестное поле - ошибка при загрузке шаблона.
- Хеш промпта (`Prompt.Hash()`) - первые 12 hex-символов SHA-256 от имён и содержимого `system.txt` и `user.tmpl`; он входит в снимок конфигурации как `prompt.hash` (`snapshot.Hashes.Prompt`), имя - как `prompt.name`.

## Конфигурация стенда и `config_id`

`internal/snapshot` (PLT-12) собирает снимок конфигурации при старте и раз в `APP_CONFIG_REFRESH_S`. `config_id` - первые 12 hex-символов SHA-256 от канонического JSON снимка: ключи отсортированы, без пробелов, числа в исходной записи. Снимок отдаёт `GET /v1/config` в виде `{"config_id", "collected_at", "config"}`.

```json
{
  "placement": "B",
  "describer_mode": "llm",
  "services": {"detector": <GET /v1/info>, "asr": <GET /v1/info>, "tts": <GET /v1/info>},
  "llm": {"url": "https://polza.ai/api/v1", "model": "<APP_LLM_MODEL>"},
  "prompt": {"name": "default", "hash": "<хеш шаблона промпта>"},
  "generation": {"temperature": 0, "top_p": 1, "seed": 42, "max_tokens": 96, "extra_body": {}},
  "timeouts_ms": {"detect": 400, "asr": 2000, "llm_ttft": 900, "llm_total": 5000, "tts_first_chunk": 1000, "request_deadline": 8000, "passive_deadline": 1500},
  "hazard_rules_hash": "<хеш правил опасности>",
  "intents_hash": "<хеш фраз намерений>",
  "tts_voice": "",
  "image": {"max_side": 640, "jpeg_quality": 80}
}
```

- `placement` - метка варианта размещения `APP_PLACEMENT`, всегда на верхнем уровне: по ней сравниваются снимки вариантов A и B.
- `llm` - только в режимах `llm` и `vlm`. `url` - схема, хост и путь `APP_LLM_URL` без логина, пароля, параметров запроса и завершающего `/`. `model` - `APP_LLM_MODEL`, а в режиме `vlm` - `APP_VLM_MODEL`, если он задан. Список `/models` поставщика и модель из его ответа в снимок не входят.
- `extra_body` - разобранный `APP_LLM_EXTRA_BODY`: порядок ключей и пробелы на `config_id` не влияют. Не JSON-объект - ошибка старта.
- Хеши промпта, правил опасности и фраз намерений передают пакеты, которые загружают эти файлы.
- Если сервис не ответил на `/v1/info`, в снимке остаётся его последний известный ответ, поэтому короткий сбой не меняет `config_id`. До первого ответа на месте сервиса стоит `null`.
- Секретов в снимке нет: ни токенов сервисов, устройств и админа, ни `APP_LLM_API_KEY`, ни `APP_POSTGRES_DSN`.

## Схема базы данных

Журнал запросов хранится в PostgreSQL (PLT-11 в [docs/spec.md](docs/spec.md)), колонки именуются в snake_case. Снимки и аудио не сохраняются никогда: запрос хранит только размер полученного снимка.

**Миграции.** SQL-файлы `migrations/NNNN_<имя>.sql` встраиваются в бинарник и применяются при старте журнала по порядку имён. Применённые версии записываются в таблицу `schema_migrations`; файл и запись о его версии выполняются одной неявной транзакцией, поэтому в файле нет `BEGIN` и `COMMIT`. Выпущенная миграция не меняется, изменение схемы - новый файл. Если база при старте недоступна, Шлюз работает дальше, а миграции повторяются перед следующей записью.

**Запись.** Асинхронная: запрос кладёт запись в буфер ёмкостью `APP_JOURNAL_BUFFER` и не ждёт базу. Один писатель забирает записи пачками до 100 штук и пишет пачку одной транзакцией. Записи отбрасываются со счётчиком `alv_journal_dropped_total`, если буфер полон или база не ответила за 5 с. В лог в этих случаях пишется предупреждение не чаще раза в 10 с с числом отброшенных записей. Если база отклонила пачку (например, нарушено ограничение), записи пишутся по одной, и теряются только отклонённые. Повторные записи с тем же ключом игнорируются.

Журнал пишется с потерями, поэтому внешние ключи связывают только строки одной записи: сессию с устройством, этапы - с запросом. Запросы потерянной сессии сохраняются.

| Таблица | Колонки | Описание |
|---|---|---|
| `device` | `device_id` (PK), `first_seen_at`, `last_seen_at` | Устройство по псевдониму - случайному UUID приложения; первое и последнее появление |
| `session` | `session_id` (PK, UUID), `device_id` (FK), `app_version`, `network`, `label`, `started_at`, `ended_at` | WebSocket-сессия; `label` - код участника испытаний (EXP-6), пусто - нет |
| `request` | `request_id` (PK, UUID), `session_id`, `kind`, `describer_mode`, `intent`, `status`, `error_code`, `degraded_reason`, `image_bytes`, `transcript`, `answer_text`, `hazard`, `objects` (JSONB), `config_id`, `llm_model`, `llm_system_fingerprint`, `llm_error`, `created_at` | Запрос: вид (`describe`, `ask`, `passive`), режим описания, итоговый статус (`ok`, `degraded`, `error`, `cancelled`, `skipped`, `stale`, `clear`), поля поставщика языковой модели; индексы по `created_at`, (`config_id`, `created_at`) и `session_id` |
| `stage_timing` | `request_id` (FK), `stage`, `duration_ms` | Длительность этапа PLT-14, мс |
| `client_metric` | `request_id`, `name`, `value` | Метрика из `client.metrics` |
| `config_snapshot` | `config_id` (PK), `config` (JSONB), `collected_at` | Снимок конфигурации PLT-12 без секретов и время, когда он собран впервые |
| `schema_migrations` | `version` (PK), `applied_at` | Применённые миграции |

## Заглушка поставщика `cmd/fakellm`

OpenAI-совместимая заглушка языковой модели для тестов и сквозной проверки без ключей и сети (PLT-19). Адрес для Шлюза - `APP_LLM_URL=http://<хост>:<порт>/v1`.

- `POST /v1/chat/completions` - только `stream: true` (иначе `400 BAD_REQUEST`). Детерминированный текст потоком SSE в формате Polza.ai: комментарий `: PROCESSING`, фрагмент с ролью, после задержки первого токена - фрагменты `chat.completion.chunk` по словам с `model` и `system_fingerprint: fp_fake`, фрагмент с `finish_reason: "stop"`, фрагмент `usage` с пустым `choices`, `data: [DONE]`.
- `GET /v1/models` - список из одной модели.
- `GET /health` - `200` и `OK`, без ключа; в `Requests()` не попадает.
- Ошибки - в формате Polza.ai: до потока `{"error": {"code": "...", "message": "...", "trace_id": "fake-trace"}, "trace_id": "fake-trace"}`, в потоке - фрагмент с `id` `error_fake`, полем `error`, `trace_id` и `finish_reason: "error"`, за которым идёт `data: [DONE]`.

```bash
go run ./cmd/fakellm --port 8090 --fail stream_error_after_sentence
```

Флаги главнее переменных окружения:

| Переменная | Флаг | Описание | По умолчанию |
|---|---|---|---|
| `FAKELLM_PORT` | `--port` | Порт HTTP | `8000` |
| `FAKELLM_MODEL` | `--model` | Модель во фрагментах и в `/v1/models` | `fake/fake-llm` |
| `FAKELLM_API_KEY` | `--api-key` | Ключ: если задан, запрос без `Authorization: Bearer <ключ>` получает `401 UNAUTHORIZED` | пусто |
| `FAKELLM_FIRST_TOKEN_DELAY_MS` | `--first-token-delay-ms` | Задержка первого токена (мс) | `0` |
| `FAKELLM_TOKEN_DELAY_MS` | `--token-delay-ms` | Задержка между токенами (мс) | `0` |
| `FAKELLM_FAIL` | `--fail` | Режим отказа, см. ниже | `none` |
| - | `-healthcheck` | Только проверить `GET http://127.0.0.1:<FAKELLM_PORT>/health` запущенной заглушки и выйти с кодом 0 или 1 | - |

| `FAKELLM_FAIL` | Поведение |
|---|---|
| `none` | обычный поток |
| `http_402` | до потока: 402, `code` `INSUFFICIENT_BALANCE` |
| `http_429` | до потока: 429, `Retry-After: 1`, `code` `TOO_MANY_REQUESTS` |
| `http_500` | до потока: 500, `code` `INTERNAL_ERROR` |
| `stream_error_before_text` | статус 200, первым фрагментом - событие ошибки `SERVICE_UNAVAILABLE`, затем `[DONE]` |
| `stream_error_after_sentence` | статус 200, первое предложение, событие ошибки `SERVICE_UNAVAILABLE`, `[DONE]` |
| `stream_402_after_sentence` | статус 200, первое предложение, событие ошибки `INSUFFICIENT_BALANCE`, `[DONE]` |
| `disconnect_after_sentence` | статус 200, первое предложение, затем обрыв соединения без `finish_reason` и `[DONE]` |
| `empty` | статус 200, сразу фрагмент с `finish_reason: "stop"` и `[DONE]`, текста нет |

Тесты поднимают заглушку в процессе: `httptest.NewServer(fakellm.NewServer(fakellm.Config{...}))`. `Config.Text` подменяет текст ответа, `Requests()` отдаёт полученные запросы (последние 256) с заголовками и телами.

## Замер поставщика `cmd/llmbench`

Замер поставщика языковой модели (LLM-4, PLT-19) тем же клиентом, что у Шлюза (`internal/llm`): последовательные потоковые запросы с эталонным промптом, сначала `--warmup` прогревочных (в статистику не входят), затем `--n` замеряемых. Результат - одна строка JSON общей схемы замеров (EXP-2) в stdout или в файл `--out`; диагностика - в stderr.

```bash
APP_LLM_API_KEY=... go run ./cmd/llmbench --url https://polza.ai/api/v1 --model <модель> --warmup 5 --n 50 > llmbench.json
```

| Флаг | Описание | По умолчанию |
|---|---|---|
| `--url` | Адрес поставщика, заменяет `APP_LLM_URL` | `APP_LLM_URL` |
| `--model` | Модель, заменяет `APP_LLM_MODEL` (с `--image` - `APP_VLM_MODEL`, если он задан) | из переменных |
| `--n` | Число замеряемых запросов | `50` |
| `--warmup` | Число прогревочных запросов | `5` |
| `--image` | JPEG-снимок: добавляется в сообщение пользователя как `image_url` с data URL, как в режиме `vlm` | нет |
| `--out` | Файл результата; пусто - stdout | пусто |

- Остальные настройки поставщика - те же переменные `APP_LLM_*`, что у Шлюза: ключ `APP_LLM_API_KEY`, параметры генерации, `APP_LLM_EXTRA_BODY` и таймауты. Первый токен позже `APP_LLM_TTFT_TIMEOUT_MS` (900 мс по умолчанию) - отказ `timeout_ttft`, как у Шлюза; чтобы замерить медленного кандидата целиком, таймаут поднимают на время замера.
- Эталонный промпт - `testdata/llmbench/prompt.json`, путь относительно рабочего каталога (корень репозитория или `/` образа со смонтированным `testdata/llmbench`). В файле промпт построителя описателя (`prompts/default`) для типичной сцены у перехода: `messages` - режим `llm`, `image_messages` - режим `vlm`, к последнему сообщению которого `--image` добавляет снимок. Оценка сверху - не больше 600 токенов; настоящее число показывает `prompt_tokens` из ответа поставщика. После изменения промпта или словаря файл пересобирается: `go test ./internal/llmbench -run '^TestPromptFile$' -update`.
- Поля результата: `service` (`llm`), `backend` (хост адреса поставщика), `model` (запрошенная модель), `device` (`null`), `git_sha`, `n`, `warmup`, `p50_ms`, `p95_ms`, `mean_ms`, `std_ms` - по TTFT; `hardware` (процессор машины замера), `started_at`; `first_sentence_p50_ms` и `first_sentence_p95_ms` - от первого токена до фрагмента, которым кончается первое предложение (`.`, `!`, `?`, `…` перед пробелом или в конце текста); `tokens_per_s` - скорость генерации после первого токена (по `usage.completion_tokens`, без него - по фрагментам); `prompt_tokens`; `response_models` - разные значения `model` из ответов; `errors` - число отказов по каждому виду PLT-15, прогрев включительно; `measured_from` - имя хоста.
- Перцентили - nearest-rank, стандартное отклонение - выборочное, как в `/v1/stats`. Задержки - в миллисекундах с одним знаком после запятой; если удачных замеряемых запросов нет, они `null`.
- Код выхода: `0` - все запросы удачны; `1` - хотя бы один запрос (в том числе прогревочный) завершился отказом или пустым ответом, или замер не запустился (нет модели, промпта, снимок не JPEG); `2` - неверные флаги. При отказах JSON всё равно печатается.
- Логи клиента выключены: stdout отдан под JSON.

## Имитатор приложений `cmd/loadgen`

Нагрузочный прогон и замер E2E по настоящему протоколу `alv.v1` (PLT-19): `loadgen` открывает сессии WS или WSS с подпротоколом `alv.v1` и токеном устройства, говорит `hello` и гоняет манифест набора данных EXP-1 в сценариях `describe` (описание по касанию: `mode=on_demand`, `focus=all`), `ask` (вопрос: `ask.start` с `trigger=hold`, снимок вопроса, если у него есть `image_id`, кадры AUDIO_IN по 100 мс, `ask.end`) и `passive` (`describe` с `mode=passive`, `focus=ahead`). Один прогон - полный проход манифеста: `describe` каждого снимка, `ask` каждого вопроса, `passive` каждого снимка. Сессии берут запросы из общей очереди по одному, между запросами сессии - пауза. Каждый прогон открывает свои сессии, поэтому смена `config_id` между прогонами видна в `welcome`. `client.metrics` не отправляется: E2E в `/v1/stats` - только с телефонов, время `loadgen` - в его JSONL.

```bash
go run ./cmd/loadgen --url ws://127.0.0.1:8080/v1/session --token <токен устройства> \
  --runs 3 --first-run 1 --sessions 1 --pause-ms 500 --out requests.jsonl --summary summary.json
```

| Флаг | Описание | По умолчанию |
|---|---|---|
| `--url` | Адрес `/v1/session`, `ws://` или `wss://` (TLS проверяется по системным корневым сертификатам) | `ws://127.0.0.1:8080/v1/session` |
| `--token` | Токен устройства; пусто - без `Authorization` (`APP_AUTH_DISABLED=true`) | `$LOADGEN_TOKEN` |
| `--dataset` | Каталог набора EXP-1: `annotations.json`, `images/`, `questions.jsonl`, `questions/` | `testdata/minidataset` |
| `--scenarios` | Сценарии через запятую: `describe`, `ask`, `passive` | все три |
| `--sessions` | Число одновременных сессий | `1` |
| `--pause-ms` | Пауза между запросами сессии, мс | `0` |
| `--runs` | Число прогонов | `1` |
| `--first-run` | Номер первого прогона: прогоны, запущенные отдельно в разное время, нумеруются без совпадений | `1` |
| `--warmup` | Прогревочные `describe` до первого прогона в отдельной сессии, в JSONL и сводку не входят | `5` |
| `--timeout-ms` | Предел запроса от отправки входа до последнего сообщения, мс | `30000` |
| `--describer-mode` | `APP_DESCRIBER_MODE` Шлюза (`template`, `llm`, `vlm`): `llm_fallback_share` считается только для `llm` и `vlm` | `llm` |
| `--out` | Файл JSONL по запросам (обязательный) | нет |
| `--summary` | Файл сводки; пусто - stdout | пусто |
| `--strict` | Код выхода 1, если есть ошибки или ответ с текстом без аудио или без `timings` (сквозная проверка DEP-8) | выключен |

- Строка JSONL - один запрос: `run` (номер прогона с учётом `--first-run`), `kind`, `image_id`, `question_id`, `request_id`, `config_id` (из `welcome` сессии), `sent_at` (UTC, момент отправки входа: сообщение `describe` или `ask.end` - конец речи, триггер вопроса по PLT-14), `accepted_ms`, `first_audio_ms`, `end_ms` (от `sent_at` до `accepted`, первого кадра AUDIO_OUT и `answer.end`, `passive.clear` или `error`; `null`, если не было), `timings` Шлюза, `text`, `intent`, `status` (`ok`, `degraded`, `error`, `clear`, `skipped`, `stale` - как в журнале), `degraded`, `degraded_reason`, `error_code` (код PROTO-11, `loadgen_timeout` или `loadgen_connection`), `audio_bytes`. JSONL с текстами ответов вне мини-набора не коммитится (NFR-8).
- Сводка - JSON с ключами `config_ids` (все `config_id` в порядке появления), `sessions`, `pause_ms`, `runs`, `pooled`, `spread`, `llm_fallback_share_limit` (0.1), `llm_fallback_share_ok`. У каждого элемента `runs` - `run`, `started_at`, `finished_at` (UTC), `requests` (число по видам), `errors` (число по кодам), `first_audio` (время до первого аудио) и `stages` (этапы `timings`) - `n`, `p50`, `p95`, `mean`; `degraded` - `n` и `share` (доля от ответов `answer.end`) по каждому `degraded_reason`; `llm_fallback_share`. `pooled` - то же по объединению прогонов (без `run`), `spread` - `p50_min`, `p50_max`, `p95_min`, `p95_max` по прогонам для `first_audio` и каждого этапа.
- Перцентили, средние и `llm_fallback_share` считает пакет `internal/stats` - так же, как `/v1/stats`. `llm_fallback_share_ok` - проверка объединения прогонов, `fallbacks*100 <= 10*answers`; без ответов описания сцены (режим `template`) доля и проверка - `null`.
- Код выхода: `0`; `1` - набор не читается, прогрев не смог подключиться, прогон прерван или не прошла проверка `--strict`; `2` - неверные флаги. Сводка печатается и при ошибках запросов.

### Встроенный мини-набор

`testdata/minidataset/` - набор в формате EXP-1 для тестов и сквозной проверки: 5 снимков 640 пикселей по длинной стороне (3 в помещении, 2 на улице), 2 вопроса WAV PCM 16 кГц моно (`quiet` и `street_noise`), разметка COCO с атрибутами `direction` и `distance` и эталонные описания. Снимки подобраны так, что детектор на бэкенде `fake` даёт на них все три свои сцены: `img001.jpg` - ступени впереди (предупреждение пассивного режима), `img002.jpg` и `img003.jpg` - комната без опасностей (`passive.clear`), `img004.jpg` и `img005.jpg` - улица. Источники и лицензии (CC0, CC BY, общественное достояние) - в `testdata/minidataset/SOURCES.md`. `testdata/llmbench/scene.jpg` - копия `img002.jpg` без людей для живой проверки режима `vlm`.

## Оценка ответов `cmd/score`

Оценка текстов ответов `loadgen` по разметке набора (PLT-19, EXP-4) и вердикт по гипотезе (EXP-8). Вход - один или несколько файлов JSONL `loadgen` (например, по файлу на прогон), результат - JSON в stdout или в файл `--out`, диагностика - в stderr.

```bash
go run ./cmd/score --dataset <каталог набора> --vocabulary vocabulary.json \
  --stats stats.json run1.jsonl run2.jsonl run3.jsonl > score.json
```

| Флаг | Описание | По умолчанию |
|---|---|---|
| `--dataset` | Каталог набора EXP-1: `descriptions.jsonl` с ключевыми объектами (обязательный) и `annotations.json` COCO со сценами и всеми размеченными объектами | `testdata/minidataset` |
| `--vocabulary` | Словарь детектора - сохранённый ответ `GET /v1/vocabulary` детектора стенда: шаблоны упоминаний `mentions` и признак `key` | `testdata/contracts/objects-detector/vocabulary.response.json` |
| `--stats` | Сохранённый ответ `GET /v1/stats?config_id=...` за время прогонов: добавляет блок `hypothesis` | нет |
| `--out` | Файл результата; пусто - stdout | пусто |

- Прогоны различаются по полю `run`. Один номер прогона в двух файлах - ошибка: прогоны, запущенные отдельно, нумеруются через `loadgen --first-run`.
- Оцениваются ответы описания по касанию (`kind=describe`) со статусом `ok` или `degraded`: только они описывают всю сцену. Запросы `describe` без `answer.end` (ошибка, таймаут) считаются в `unanswered` и не оцениваются; `ask` и `passive` пропускаются.
- Текст режется на предложения после `.`, `!`, `?`, `…` перед пробелом или в конце текста и нормализуется по PLT-4. Упоминание класса - совпадение с шаблоном `mentions` словаря целыми словами. Направления: `left` - «слева», «налево», «левее», «по левую руку», «с левой стороны»; `ahead` - «впереди», «спереди», «прямо», «перед вами», «перед тобой»; `right` - «справа», «направо», «правее», «по правую руку», «с правой стороны».
- Метрики EXP-4:
  - `key_objects_with_direction` - ключевой объект назван верно, если в одном предложении упомянут его класс и названо его направление; сумма верно названных делится на сумму ключевых объектов (микроусреднение). Два объекта одного класса считаются по отдельности;
  - `key_objects_class_only` - то же без направления: класс упомянут где-либо в ответе;
  - `hallucinated` - упоминание - пара «предложение, ключевой класс» (`key: true` в словаре); выдуманное - класса нет ни в `annotations.json` снимка, ни в его ключевых объектах; число выдуманных делится на все упоминания.
- Ключи результата: `config_ids`, `files`, `runs` (по прогонам, с `run`), `pooled` (объединение прогонов), `spread` (`min`, `max`, `mean` каждой доли по прогонам), `images` (по снимкам за все прогоны, с `image_id` и `scene`), с `--stats` - `hypothesis`. У итогов - счётчики `answers`, `unanswered`, `key_objects`, `named_with_direction`, `named_class_only`, `mentions`, `hallucinated_mentions` и доли `key_objects_with_direction`, `key_objects_class_only`, `hallucinated` (`null` без знаменателя).
- Блок `hypothesis` (EXP-8): `config_id`, `runs`, `e2e_p95_ms` (p95 `e2e.describe` из `/v1/stats`, `null` без замеров), `e2e_p95_limit_ms` (2000), `key_objects_with_direction` (объединение прогонов), `key_objects_limit` (0.75), `llm_fallback_share` (из `/v1/stats`), `llm_fallback_share_limit` (0.1), `checks` (`e2e`, `quality`, `fallbacks`; `null` для отсутствующей величины), `verdict`:
  - `confirmed` - выполнены все три условия не меньше чем на трёх прогонах;
  - `not_confirmed` - хотя бы одна проверка не выполнена (даже если другой величины нет);
  - `insufficient_data` - ни одна проверка не провалена, но какой-то величины нет или прогонов меньше трёх.

  Границы включены, сравнения целочисленные: `named_with_direction*100 >= 75*key_objects`; p95 и доля откатов переводятся в миллионные доли единицы с округлением и сравниваются с порогом как целые. `config_id` блока - из `/v1/stats`; если в JSONL есть другой `config_id`, это ошибка. Без `config_id` в `/v1/stats` берётся единственный `config_id` JSONL.
- Автоматическая оценка перепроверяется вручную на 10 % ответов (EXP-4).
- Код выхода: `0` - результат напечатан (при любом вердикте); `1` - вход не читается или противоречив (повтор номера прогона, снимок без описания, класс не из словаря, чужой `config_id`); `2` - неверные флаги или нет файлов JSONL.
- Игрушечные данные тестов - `testdata/score/`: `metrics/` (3 снимка, два прогона в двух файлах и файл с повтором прогона) и `verdict/` (20 снимков по одному ключевому объекту, `quality90`, `quality75`, `quality74.jsonl` по 5 прогонов и сохранённые ответы `/v1/stats` для случаев вердикта).

## Развёртывание

Файлы compose для вариантов размещения A и B и стенда на заглушках, Caddy с TLS, примеры туннеля WireGuard, прокси gpt2giga с сертификатом НУЦ, загрузка весов и живая проверка поставщиков - в [deployments/README.md](deployments/README.md).

Образ distroless, в нём нет shell и curl, поэтому healthcheck контейнеров `gateway` и `fakellm` - сам бинарник: `/gateway -healthcheck` проверяет `GET http://127.0.0.1:${APP_SERVER_PORT}/health`, `/fakellm -healthcheck` - то же на `FAKELLM_PORT`; код выхода 0 или 1.

## Разработка

Подготовка машины - [docs/development.md](docs/development.md): Go 1.24.13 и moq ставит `scripts/setup-dev-env.sh`.

### Запуск тестов

Моки (`*_moq_test.go`) генерируются по директивам `//go:generate moq` и в git не попадают, поэтому на чистом клоне сначала нужны моки:

```bash
./scripts/regenerate-mocks.sh
go test -p 1 ./...
```

### Интеграционные тесты

Репозиторий журнала проверяется на настоящем PostgreSQL. Тесты помечены тегом сборки `integration` и в обычный `go test ./...` не входят. Скрипт генерирует моки, поднимает `postgres:17-alpine` в Docker на свободном порту `127.0.0.1`, прогоняет `TestRepository` и удаляет контейнер при любом исходе:

```bash
./scripts/test-integration.sh
```

Нужны Docker, Go и moq. Образ меняет переменная `ALV_TEST_POSTGRES_IMAGE`. С уже запущенной базой тесты запускаются так (схема `public` базы очищается):

```bash
APP_TEST_POSTGRES_DSN="postgres://postgres:<пароль>@127.0.0.1:5432/alv_test?sslmode=disable" \
  go test -tags integration -v -run '^TestRepository$' ./internal/journal/
```

### Проверки как в CI

```bash
./scripts/regenerate-mocks.sh
test -z "$(gofmt -l .)"
go vet ./...
go test -p 1 ./...
```

CI (`.github/workflows/ci.yml`) делает то же на каждый pull request и на push в `dev`. Workflow `.github/workflows/release.yml` на push в `main` и на теги `v*` прогоняет тесты и публикует образ в `ghcr.io/nikarpoff/assistant-low-vision-platform` с тегами `latest` (только `main`), `sha-<7 символов>` и `v<semver>`.

### Сборка

```bash
go build ./...
docker build -f build/Dockerfile -t alv-platform:test .
```

Образ собирает все бинарники `cmd/*` в корень: `/gateway` - точка входа, остальные инструменты запускаются заменой `entrypoint`.

### Контракты сервисов

Этот репозиторий - источник истины для эталонных примеров сервисов (`testdata/contracts/<сервис>/`) и векторов протокола (`testdata/protocol/vectors.json`). Копии в репозиториях сервисов и приложения вручную не правятся:

```bash
scripts/sync-contracts.sh          # скопировать в соседние репозитории общего проекта
scripts/sync-contracts.sh --check  # сверить копии, ненулевой код при расхождении
```

### Форматирование

```bash
gofmt -w .
goimports -w .
go vet ./...
```
